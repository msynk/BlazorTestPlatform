# Visual regression testing services and accessibility testing/monitoring tools (2025-2026): concrete features and UX patterns

Scope: Percy (BrowserStack), Applitools Eyes, Chromatic (visual + accessibility), Lost Pixel, Argos CI, Happo, Playwright `toHaveScreenshot`, Storybook Visual Tests addon, Deque axe DevTools / IGT / axe Monitor / axe Developer Hub, Lighthouse CI, Pa11y / Pa11y CI / Pa11y Dashboard, Siteimprove / Level Access (brief), Microsoft Accessibility Insights. Research date: 2026-11-10. Context for inferences: BlazorTestPlatform (BTP) already has per-story screenshots across viewports/themes/Chromium/Firefox/WebKit, a YIQ perceptual diff with masks, thresholds and anti-aliasing detection, git-stored baselines, `btp approve`, a slider diff viewer in an HTML report, axe-core in browsers plus 37 bUnit markup rules, justified/expiring a11y suppressions, and a manual WCAG 2.2 review workflow whose fingerprints mark reviews stale.

## Q1. Visual review UX: diff view modes, grouping, bulk accept, review states, comments, branch baselines, ignore regions, dynamic content, cross-browser grids, PR checks

### Takeaway
Every hosted service converges on: a baseline-vs-new view with a 2-up (split) mode and a 1-up overlay with a neon or red highlight, a per-snapshot accept/reject plus a build-level verdict, a PR status check, and baselines chosen from the git merge base. The 2025-2026 differentiators are grouping identical or similar diffs so one decision covers many snapshots (Argos "N similar", Happo grouped rows, Applitools "Group by similar differences", Percy "Approve groups of matching visual changes"), decisions that persist across commits, keyboard-driven review (Argos Y/N/I/G/J/K), flaky-change fingerprints with auto-ignore, and AI triage (Percy Visual Review Agent). A slider/swipe mode is not documented by Chromatic or Argos, so BTP's existing slider is uncommon. Split, overlay and strobe are the table-stakes modes BTP is missing.

### Cited Findings

**Chromatic: diff inspector (view modes)**
- Modes: "Unified view (1 Up)" overlays changes on the baseline. "Split view (2 Up)" shows baseline and new snapshot side by side, with changes highlighted in the new one. — [Chromatic Diff Inspector](https://www.chromatic.com/docs/diff-inspector)
- Changed areas are highlighted in neon green. "Diff strobing" (also called "party mode") toggles rapidly between baseline and new to emphasize the change. — [Chromatic Diff Inspector](https://www.chromatic.com/docs/diff-inspector)
- "Autofocus" turns on automatically when only minimal pixel variations are found and spotlights the minor change. In focus mode, hovering the new snapshot shows a magnifying glass. — [Chromatic Diff Inspector](https://www.chromatic.com/docs/diff-inspector)
- `diffThreshold` can be set at project, story, test, or Cypress level. Elements with the `chromatic-ignore` class or data attribute are excluded, and ignored regions can be highlighted in the Diff Inspector. — [Chromatic Diff Inspector](https://www.chromatic.com/docs/diff-inspector)
- SteadySnap stabilizes rendering. Tests that still render inconsistently are flagged "unstable" and do not block the build. Cross-browser coverage is Chrome, Firefox, Safari and Edge. Storybook Globals ("modes") test variants across themes, viewports, locales and media features. — [Chromatic: Why Chromatic](https://www.chromatic.com/docs/test)
- TurboSnap snapshots only the tests affected by a change, using Git history and the bundler dependency graph. Chromatic claims up to 80% lower usage cost (vendor claim). — [Chromatic: Why Chromatic](https://www.chromatic.com/docs/test)

**Chromatic: branch baselines (UI Tests)**
- Baselines are per branch. A new branch inherits the baseline of the commit it branched from. For a new build, Chromatic finds the nearest git ancestor that has a Chromatic build. — [Chromatic Branching and baselines](https://www.chromatic.com/docs/branching-and-baselines)
- Per-snapshot rule: if the ancestor snapshot was unchanged, or changed and accepted, it becomes the baseline. If it was denied or is still pending, Chromatic uses that snapshot's own baseline, so a reverted change compares cleanly. — [Chromatic Branching and baselines](https://www.chromatic.com/docs/branching-and-baselines)
- With multiple ancestors (merge commits), the most recently accepted candidate wins. The account-wide `preferMergedBaselines` flag (enabled by support) instead favors incoming baselines such as those from `main`. — [Chromatic Branching and baselines](https://www.chromatic.com/docs/branching-and-baselines)
- Squash and rebase merges are detected through git provider APIs (for GitHub, via the GitHub App), and accepted baselines from the PR head carry over. `--auto-accept-changes` or `autoAcceptChanges: "main"` auto-accepts changes on main. — [Chromatic Branching and baselines](https://www.chromatic.com/docs/branching-and-baselines)
- Baselines are browser-independent: accepting a baseline accepts the snapshots from all browsers. — [Chromatic Branching and baselines](https://www.chromatic.com/docs/branching-and-baselines)
- Baseline history UI: when reviewing a change, the dashboard shows the story's historical baselines, labels the "Most recent build" and the "current baseline", and shows who accepted each and in which commit. Build pages list "Ancestor Builds". Individual builds cannot be deleted. — [Chromatic Branching and baselines](https://www.chromatic.com/docs/branching-and-baselines)

**Chromatic: UI Review (PR-level review, separate from UI Tests)**
- The Changeset tab compares the latest PR-branch commit with the merge-base commit, side by side, with a toggleable highlighted diff. Threaded discussions are attached to each snapshot and closed with "Resolve". — [Chromatic UI Review](https://www.chromatic.com/docs/review/)
- The checklist requires three things: the changeset approved, discussions resolved, and all assigned reviewers approved. The states are "Pending" and "Passed". There are default reviewers (all must approve) and component owners that auto-assign reviewers by changed components. — [Chromatic UI Review](https://www.chromatic.com/docs/review/)
- Each PR gets a "UI Review" status check that can be made required in GitHub, GitLab or Bitbucket. Chromatic cannot prevent self-approval. — [Chromatic UI Review](https://www.chromatic.com/docs/review/)

**Storybook Visual Tests addon (Chromatic)**
- A "Play" button in the Storybook sidebar runs visual tests and shows progress. Stories with changes are highlighted yellow in the sidebar, and the addon panel shows "which pixels changed". — [Chromatic Visual Tests addon](https://www.chromatic.com/docs/visual-tests-addon)
- You can accept changes locally as baselines and undo with an "Unaccept" button. Deny is not available in the addon, only for CI/CLI builds. Accepted local baselines sync to the cloud. The addon requires Storybook 7.6+, and its snapshots count toward the Chromatic plan. — [Chromatic Visual Tests addon](https://www.chromatic.com/docs/visual-tests-addon)

**Argos: build review UI (most detailed keyboard-driven UX found)**
- Modes: "Split view" (default, `S`), "Single view" (switch between "Baseline" and "Changes"), "Changes overlay" (red highlight, `D`, color and opacity configurable in the toolbar), and "Highlight changes" (flashes changed regions, `H`; `J`/`K` jump between regions). `←`/`→` show only the baseline or only the changes. — [Argos: Review a build](https://argos-ci.com/docs/learn/review-workflow/review-a-build)
- "ARIA view" switches between the screenshot and its accessibility tree when an ARIA snapshot exists. — [Argos: Review a build](https://argos-ci.com/docs/learn/review-workflow/review-a-build)
- `Space` fits or expands the image. Zoom and pan are synced between the panes. `↑`/`↓` move between snapshots, and `⇧+←/→` move between journey steps. A "Journey" toolbar strip shows every step of a multi-screen test, including unchanged steps. — [Argos: Review a build](https://argos-ci.com/docs/learn/review-workflow/review-a-build)
- `Y`/`N` mark a change accepted or rejected, and `I` ignores a flaky change. The build-level verdict ("Comment", "Reject" or "Approve") is submitted from a review popover. — [Argos: Review a build](https://argos-ci.com/docs/learn/review-workflow/review-a-build)
- Grouping: diffs with the same fingerprint share one row with an "N similar" button. Accepting or rejecting a collapsed row applies to every screenshot in the group, and `G` expands it. — [Argos: Review a build](https://argos-ci.com/docs/learn/review-workflow/review-a-build)
- Comments are pinned to a point on a screenshot (or to selected lines of a text snapshot). They support Markdown, `/` slash commands, @mentions, emoji reactions, and resolve/reopen. Comments stay a private pending review until submitted; hold Alt to post immediately. — [Argos: Review a build](https://argos-ci.com/docs/learn/review-workflow/review-a-build)
- Reviewer states are Approved, Rejected, Commented, Pending and Dismissed. Only each reviewer's latest review counts, one active rejection makes the build rejected, and otherwise one approval makes it approved. Submitting a review is disabled in a merge queue, for auto-approved builds, and when there are no changes. — [Argos: Review a build](https://argos-ci.com/docs/learn/review-workflow/review-a-build)
- Other surfaces: a builds list, a PR comment with the latest build status, summary commit checks, Tags to filter screenshots, "Review builds with AI agents", and Automations that notify Slack, Microsoft Teams or Discord. — [Argos review workflow index](https://argos-ci.com/docs/learn/review-workflow.md)
- Flaky handling: each change gets a fingerprint from the shape of its diff, and an ignore applies to a test-plus-fingerprint pair. Auto-ignore (Project Settings, Flaky detection) treats a change as flaky once it appears at least N times (default 3) in auto-approved builds within the last 7 days. An "Ignored changes" page lists how often each ignored change still fires. CLI: `change ignore`/`change unignore`, `--auto-ignore-after off`. — [Argos flaky test detection](https://argos-ci.com/docs/learn/reliability-and-flakiness/flaky-test-detection); [Argos changelog](https://argos-ci.com/changelog) (search summary)
- Argos also deploys a Storybook or static-site preview per PR and compares non-image files. It is MIT-licensed on GitHub, but self-hosting is not officially supported or documented. — [Argos docs](https://argos-ci.com/docs)

**Argos: baseline selection (precise rules)**
- A candidate baseline build must have finished processing, have no failed tests, not be a subset build, and have no active rejection. It must also share the build name and mode, and sit on the merge base or an ancestor of it. — [Argos baseline build](https://argos-ci.com/docs/learn/platform-fundamentals/baseline-build.md)
- Search order: (1) a build on the merge-base commit or `ARGOS_REFERENCE_COMMIT` (approval not required); (2) the closest approved build on an ancestor, searched up to 5,000 commits; (3) an approved build on the same commit. Otherwise the build is an "orphan". — [Argos baseline build](https://argos-ci.com/docs/learn/platform-fundamentals/baseline-build.md)
- The default baseline branch is auto-approved; patterns are configurable. PR builds are never auto-approved. `ARGOS_REFERENCE_BRANCH` overrides the baseline branch. — [Argos baseline build](https://argos-ci.com/docs/learn/platform-fundamentals/baseline-build.md)

**Happo: new review experience (blog dated 2026-10-13)**
- Each diff, added snapshot and removed snapshot has its own Accept and Reject buttons. Decisions save immediately, and the header shows progress (for example "3 of 19 reviewed"). Accepting every diff accepts the comparison, and rejecting any one rejects it. — [Happo blog: new review experience](https://happo.io/blog/new-review-experience)
- Grouping: within a variant, targets (browsers) with the same change fold into one row. Across variants and components, rows where the same pixels changed collect under one entry with member thumbnails. One decision covers the group, and "Review separately" splits it. — [Happo blog](https://happo.io/blog/new-review-experience)
- Decisions are recorded against the pair of screenshots, so they persist to later commits on the same PR ("When you push a fix, the diffs you already accepted stay accepted"). — [Happo blog](https://happo.io/blog/new-review-experience)
- Image diffs: Space cycles through the highlighted changes, the before image, the after image, and an outline of the changes. Shortcuts accept, reject and go to the next diff, and `?` lists them. On phones, swiping right accepts and left rejects. — [Happo blog](https://happo.io/blog/new-review-experience)
- The dashboard is a feed of jobs grouped by day, with one row per PR. It has a five-mark "how much changed" scale per job, a filter box, and a 30-day summary of jobs, new flakes and accessibility violations. `group: true` posts a single `Happo` status check, and a named group posts `Happo (e2e)`. — [Happo blog](https://happo.io/blog/new-review-experience)
- Renderer/browser update alerts name the targets and browser versions when the before and after reports were rendered differently. Happo may re-render "before" with the "after" renderer so only your change causes diffs. The classic compare page has accept/reject in a sidebar, and the status is posted to GitHub. — [Happo: Reviewing diffs](https://docs.happo.io/docs/reviewing-diffs)

**Percy (BrowserStack)**
- Approvals can be given per build ("Approve build"), per group ("Approve groups of matching visual changes"), or per snapshot. Approval applies to the whole snapshot across all browser/width combinations. — [Percy approval workflow](https://www.browserstack.com/docs/percy/visual-testing-workflows/view-percy-build-results/approval)
- "Request changes" sets the build status to "Changes requested". Approving every snapshot approves the build and turns the Percy check "passed". Identical, previously approved snapshots keep their approval across builds on the same branch, so they need approval only once per branch. — [Percy approval workflow](https://www.browserstack.com/docs/percy/visual-testing-workflows/view-percy-build-results/approval)
- A "Visual Testing Plugin" lets AI coding agents review each build from the editor, recommend approve or reject, and gate the merge, with the user confirming each decision. — [Percy approval workflow](https://www.browserstack.com/docs/percy/visual-testing-workflows/view-percy-build-results/approval)
- Baseline picking: for PR builds, Percy uses the PR's target branch and the merge base. Without a PR, the default branch ("master") is used. The PR target overrides `PERCY_TARGET_BRANCH`. — [Percy base build selection](https://docs.percy.io/v1/docs/baseline-picking-logic) (search summary)
- Visual Review Agent (launched 2025-10-14): enabled per build with an "AI-powered build" toggle, which turns on every snapshot-level AI toggle. Each snapshot can be switched individually. Paid plans only, and it cannot run alongside Percy "Layout testing". — [Percy VRA overview](https://www.browserstack.com/docs/percy/ai-agents/visual-review-agent/overview); [SD Times](https://sdtimes.com/test/browserstack-adds-visual-review-agent-for-web-testing/)
- VRA UX: each change gets a natural-language summary. "Irregular" changes (likely bugs such as stretched images or overlapping text) get a bug icon and a red bounding box, "Valid" changes get a red box without the icon, and ignored differences get a purple box. Sorting options are "Bugs (High to Low)" (default) and "Diff % (High to Low)". — [Percy VRA overview](https://www.browserstack.com/docs/percy/ai-agents/visual-review-agent/overview)
- "Matches PR summary" / "Does not match PR summary" labels are shown for GitHub/GitLab PR builds (advisory only). Users can give thumbs up/down with an optional 120-character comment. Custom prompts are supported. Each build shows build-level ROI: the number of differences filtered as noise and the estimated review time saved. — [Percy VRA overview](https://www.browserstack.com/docs/percy/ai-agents/visual-review-agent/overview)
- Changes ignored by the agent, by Regions, or by Intelli-ignore are grouped under "Show ignored diffs" (new dashboard) or "Diffs ignored by" (classic). Drawing a region or changing diff sensitivity disables AI diff for that snapshot/browser/width. Comparisons are limited to 13,500px of height. — [Percy VRA overview](https://www.browserstack.com/docs/percy/ai-agents/visual-review-agent/overview)
- Intelli-ignore auto-detects and ignores dynamic UI elements, with a diff-sensitivity setting and a diff-ignore percentage. It is on by default for projects created after 2024-04-08. One doc version lists Strict/Recommended/Relaxed and another lists five levels. — [Percy Intelli-ignore](https://www.browserstack.com/docs/percy/visual-testing-workflows/view-percy-build-results/intelli-ignore) (search summary; conflicting doc versions)

**Applitools Eyes**
- Automated test maintenance: "Group by similar differences" groups steps whose pink diff areas match, in the same order. Steps can also be grouped by plain-English "Diff Type", which needs a captured DOM. Group thumbnails look like a deck of cards with a step counter. — [Applitools test maintenance](https://applitools.com/docs/eyes/concepts/reviewing-tests/test-maintenance)
- Group actions include "Accept group diffs", reject, and "Exclude selected steps from group". Adding, adjusting or deleting ignore, match-level or floating regions prompts "Apply to other steps in scope". Scopes are Default (same test and app name), Batch, Selected tests/steps, and Current step only. — [Applitools test maintenance](https://applitools.com/docs/eyes/concepts/reviewing-tests/test-maintenance)
- Root cause analysis: click the pink diff area and the RCA panel lists the overlapping baseline and checkpoint elements. It shows tag changes (e.g. `<button>` to `<a>`), attribute and class changes, bounding-box changes, CSS property changes (full rule with changed properties shaded) and text changes, color-coded green for added and red for removed. SHIFT+E selects an element manually, "Share RCA" copies a deep link, and RCA requires DOM capture (`sendDom`). — [Applitools RCA](https://applitools.com/docs/eyes/concepts/reviewing-tests/root-cause-analysis)
- Branch baselines live in Applitools branches. They are merged through a compare-and-merge page ("Merge" button), where conflicts can arise. A May 2026 blog describes automating merges via the Eyes Server API: check-only on PRs, the actual merge post-merge or nightly, with conflicts resolved in the dashboard first. — [Applitools help: Branches](https://help.applitools.com/hc/en-us/articles/360007528631-Branches); [Applitools blog: managing baseline branches](https://applitools.com/blog/managing-baseline-branches-using-ci-cd-pipelines/)

**Playwright `toHaveScreenshot` (OSS reference point)**
- Baselines are stored in `<testfile>-snapshots/` and named `<name>-<browser>-<platform>.png`, so browsers and platforms need separate baselines. `snapshotPathTemplate` customizes paths. Lossless WebP is optional. `--update-snapshots` rewrites baselines. When generating a baseline, Playwright screenshots repeatedly until two consecutive captures match. — [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots)
- Options: `animations` ("disabled" default), `caret` ("hide" default), `clip`, `fullPage`, `mask` (locators), `maskColor` (default `#FF00FF`), `maxDiffPixels`, `maxDiffPixelRatio`, `omitBackground`, `scale` ("css"/"device"), `stylePath` (CSS injected during capture; pierces shadow DOM and frames), `threshold` (default 0.2, YIQ), `timeout`. — [Playwright PageAssertions](https://playwright.dev/docs/api/class-pageassertions)
- `toMatchAriaSnapshot` stores YAML accessibility-tree snapshots inline or in `.aria.yml` files. — [Playwright PageAssertions](https://playwright.dev/docs/api/class-pageassertions)

**Lost Pixel**
- Modes: Storybook, Ladle, Histoire, Page Screenshots, and Custom Screenshots (bring your own Playwright/Cypress shots). There is an OSS engine (free) and a SaaS platform built on it. The platform adds monorepo support, comments, notifications and a "review & maintenance workflow". — [Lost Pixel docs](https://docs.lost-pixel.com/user-docs); [Lost Pixel OSS vs Platform](https://docs.lost-pixel.com/user-docs/readme-1.md)
- Masks are set per page (`mask: [{ selector: 'code' }]`) or globally under `pageShots`. Thresholds can be per page (e.g. `threshold: 0.1`) or at Storybook level. — [Lost Pixel blog: flaky tests](https://lost-pixel-landing.vercel.app/blog/post/handling-flaky-visual-regression-tests-with-lost-pixel-platform); [Lightrun: Lost Pixel mask issue](https://lightrun.com/answers/lost-pixel-lost-pixel-ability-to-mask-areas-of-the-application-so-visual-regression-will-not-be-compared-against-certain)

### Inferences
- Table-stakes view modes BTP lacks: Split (2-up) and Unified overlay with a configurable highlight color and opacity (Argos), strobe/flicker (Chromatic "party mode", Argos "Highlight changes"), and an only-baseline/only-new toggle. Synced zoom/pan and an autofocus magnifier for tiny diffs are cheap wins in a Blazor viewer because BTP already has the diff mask.
- BTP should compute a diff fingerprint, for example a hash of the normalized changed-region mask plus a coarse color delta. That enables three things: (a) Argos-style "N similar" grouping across stories, (b) Happo-style folding of the same change across browsers, themes and viewports into one row, and (c) flaky detection ("seen N times in 7 days" leads to suggesting a mask or ignore). All of this is local computation and fully self-hostable.
- Review decisions keyed by (story, variant, baseline hash, actual hash), as Happo and Percy do, can be stored in a git-tracked JSON file next to the baselines. `btp approve` then persists across re-runs of the same commit range without a server. This mirrors Percy's "approval carried forward on the same branch for identical snapshots".
- Because BTP baselines live in git, branch semantics come for free: the merge brings the baselines, like Chromatic's "accepted baselines come with it". The complex ancestor-build algorithms (Chromatic, Argos, Percy) are only needed for a demo site that shows history across builds. There, a simplified "latest build on merge base" rule is enough.
- Keyboard-first review (Y/N/I/G, J/K, arrows, `?` help overlay) is a low-cost, high-perceived-quality feature for a Blazor review page.
- Percy's per-build "noise filtered, time saved" counter can be approximated honestly in BTP by reporting how many pixels or snapshots were neutralized by anti-aliasing detection, masks and thresholds.
- Happo's "renderer changed" alert maps directly to BTP's multi-browser setup. Recording the browser and engine version with each baseline lets BTP flag diffs caused by a browser upgrade.

### Gaps
- Chromatic's dashboard keyboard shortcuts, the exact "Accept all" / "Accept component" bulk actions, and "Deny"/"Unreview" semantics were not covered on the fetched pages (the UI Review and diff-inspector pages omit them).
- Percy's exact diff UI modes (overlay toggle, full screen, browser/width switching) were not confirmed from official docs. Only a third-party blog mentioned an overlay, so it is unverified.
- The Playwright HTML report's image-diff UI (Diff/Actual/Expected/Side-by-side/Slider tabs) is not described in the fetched docs pages, so it is not cited here.
- Applitools Ultrafast Grid details (one capture rendered across many browser/OS/viewport combinations, with baselines tied to the execution environment) appeared only in search snippets. The specific doc page was not fetched or verified.
- The Argos status filters (Changed/Added/Removed/Failure) were not listed on the review page.

## Q2. Algorithms and approaches (pixel, perceptual, DOM-based, Visual AI, layout match) and exposed knobs

### Takeaway
OSS tools (Playwright, Lost Pixel) and most hosted CI services (Chromatic, Argos, Happo) use pixel diffs with a perceptual color tolerance (YIQ/odiff), plus thresholds, masks and stabilization. Applitools exposes semantic "match levels" (Strict, Layout, Ignore Colors, Dynamic, Exact) and per-region overrides. Percy layers AI classification (Visual Review Agent, Intelli-ignore) on top of its diff engine. DOM-aware approaches appear as Applitools RCA (DOM/CSS diff behind a visual diff), Chromatic's DOM-node-plus-bounding-box identity for a11y violations, and ARIA snapshots (Playwright, Argos). BTP's YIQ + anti-aliasing approach is the same family as Playwright's.

### Cited Findings
- Playwright compares with pixelmatch. `threshold` is a per-pixel perceived color difference in YIQ space, from 0 to 1 (default 0.2). It also exposes `maxDiffPixels` and `maxDiffPixelRatio`, and stabilizes the shot by disabling animations, hiding the caret, and retrying until two consecutive captures match. — [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots); [Playwright PageAssertions](https://playwright.dev/docs/api/class-pageassertions)
- Lost Pixel uses odiff, which is listed in the odiff README as an integration. Odiff's threshold is a color-difference value from 0 to 1, default 0.1. — [odiff-bin npm](https://www.npmjs.com/package/odiff-bin) (search summary)
- Chromatic pixel-diffs snapshots against prior versions. It exposes `diffThreshold` (project/story/test), `chromatic-ignore` regions, SteadySnap stabilization, and an "unstable" classification for flaky renders. — [Chromatic: Why Chromatic](https://www.chromatic.com/docs/test); [Chromatic Diff Inspector](https://www.chromatic.com/docs/diff-inspector)
- Applitools "Strict" detects visible changes in text, font, color, graphics and position while ignoring rendering-related pixel differences. "Layout" checks the relative positions of elements and ignores text, color and style changes; it suits dynamic content, localization and cross-environment testing. "Ignore Colors" is Strict without color. "Dynamic" validates text against patterns (text, number, date, link, email, currency, or custom patterns written as .NET regular expressions). "Exact" is pixel-to-pixel and is not recommended. — [Applitools match levels](https://applitools.com/docs/eyes/concepts/best-practices/match-levels)
- Applitools default: "Dynamic" is the default for Web tests on supported SDK versions (e.g. eyes-cypress 3.60.3+), and admins can change it. Applitools states that pixel and threshold comparison is "unreliable and noisy" and that Eyes compares by human perception. — [Applitools match levels](https://applitools.com/docs/eyes/concepts/best-practices/match-levels)
- Applitools region types: match-level regions (Strict/Layout/IgnoreColors/Dynamic/Exact for part of a checkpoint), dynamic-text regions, ignore regions (a "last resort"), and floating regions (an element may move within a larger bounds box). With Dynamic applied to the whole checkpoint, shifts of surrounding elements caused by dynamic content are ignored. — [Applitools match levels](https://applitools.com/docs/eyes/concepts/best-practices/match-levels)
- Applitools RCA maps visual diffs to DOM/CSS differences; it needs DOM capture. — [Applitools RCA](https://applitools.com/docs/eyes/concepts/reviewing-tests/root-cause-analysis)
- Percy's "Visual AI Engine" is described as the core algorithm that runs all image comparisons. Intelli-ignore adds a diff sensitivity and a diff-ignore percentage. The Visual Review Agent filters "minor, barely noticeable pixel shifts" and classifies changes as Irregular or Valid. Very large changes fall back to standard diffs. — [Percy Visual Engine](https://www.browserstack.com/percy-product/percy-visual-engine) (search summary); [Percy VRA overview](https://www.browserstack.com/docs/percy/ai-agents/visual-review-agent/overview)
- Percy also offers a separate "Layout testing" mode that cannot run together with the Visual Review Agent. — [Percy VRA overview](https://www.browserstack.com/docs/percy/ai-agents/visual-review-agent/overview)
- Argos diff fingerprints "absorb pixel-level noise such as antialiasing but distinguish genuinely different changes". They drive grouping and flaky auto-ignore. — [Argos flaky test detection](https://argos-ci.com/docs/learn/reliability-and-flakiness/flaky-test-detection) (search summary)
- Happo exposes a compare threshold ("Compare with a threshold", `compareThreshold`) and can re-render the baseline with the new renderer to remove environment noise. — [Happo: Reviewing diffs](https://docs.happo.io/docs/reviewing-diffs)

### Inferences
- BTP's YIQ + anti-aliasing diff already matches the OSS state of the art (pixelmatch class). The realistic next knobs are: `maxDiffPixelRatio`, a per-region match level (at least "layout-only" and "ignore colors"), floating regions (an element may move within bounds), and a `stylePath`-like CSS injection per story to hide volatile content.
- A "layout" mode is feasible without AI. BTP can record element bounding boxes (via JS in the browser, or from bUnit markup combined with in-browser `getBoundingClientRect`) and compare box geometry instead of pixels. That is close to Applitools Layout and Percy Layout testing in spirit.
- A "Dynamic"-style text-pattern region is attractive for .NET: Applitools itself uses .NET regex for custom patterns, and BTP could validate text nodes in a region against a `Regex` instead of comparing pixels.
- An RCA-style DOM/CSS diff is a strong, self-hostable differentiator for BTP. bUnit already produces markup per story, and the browser runner can capture computed styles for elements that intersect the diff mask. Showing "what DOM/CSS changed under this pink area" next to the slider is rare outside Applitools.
- AI classification (Percy VRA) is the hardest to self-host credibly. A heuristic version is realistic: classify a diff as "text-only", "color-only", "geometry shift" or "new/removed element" by comparing DOM and box snapshots. That gives Percy-like labels without an AI model.

### Gaps
- Chromatic's actual diff algorithm (pixel versus perceptual color space) and its anti-aliasing handling are not specified in the fetched docs.
- Argos's exact comparison algorithm and threshold are not documented on the baseline page. Happo's `compareThreshold` semantics were not fetched.
- Playwright's experimental `ssim-cie94` comparator was not confirmed in the fetched docs.
- The internals of Percy's Visual AI Engine are not documented beyond marketing descriptions.

## Q3. Accessibility UX: issue grouping, highlighting, needs review, guided manual tests, scoring/trends, baselines of known issues, per-component dashboards, VPAT/ACR export

### Takeaway
The 2025-2026 pattern is: automated axe-core results per page or component, a "needs review" (axe incomplete) bucket for humans, guided or assisted manual tests (Deque IGTs, Accessibility Insights Assessment with automated/assisted/manual requirements), baselining so that only new violations block (Chromatic a11y tests; Storybook `todo` vs `error`; Lighthouse CI and Pa11y thresholds), and dashboards with trends, component or page rankings, and CSV/JSON export that feeds VPAT/ACR documents. VPAT/ACR generation proper is mostly an enterprise or manual-audit feature (Deque axe Auditor, Level Access services).

### Cited Findings

**Chromatic accessibility tests (component-level baselines)**
- Each story has an accessibility baseline: the set of detected violations. Accepting a build adds its violations to the baseline, and later builds flag only new or changed violations. "Fixes are auto-accepted to the baseline". — [Chromatic accessibility](https://www.chromatic.com/docs/accessibility)
- Violation identity is violation type + DOM node + the node's bounding box. Chromatic says this "prevents false positives caused by inconsequential DOM structure changes." — [Chromatic accessibility](https://www.chromatic.com/docs/accessibility)
- Chrome only. Runs per mode and viewport, and TurboSnap limits runs to affected stories. axe "Incomplete" results are not reported in Chromatic (only in Storybook's panel). There are no custom axe rules, no ignore regions, no nested-iframe checks, no `prefers-reduced-motion` checks, and a11y cannot be disabled separately from visual tests. — [Chromatic accessibility](https://www.chromatic.com/docs/accessibility)
- Review UX: the results column marks a change as "visual or accessibility". The snapshot's accessibility tab lists violations as expandable accordions with details and suggested fixes. "Offending nodes are highlighted in red within the snapshot", and clicking a node shows a tooltip. A PR with new violations stays "unreviewed" until they are accepted or fixed. Builds with only fixes pass automatically. Accessibility-only changes show the latest snapshot with problem nodes highlighted, and non-visual violations (e.g. a missing `lang`) have no preview. — [Chromatic a11y usage](https://www.chromatic.com/docs/accessibility/usage)
- Previously accepted violations are hidden behind a button at the bottom of the section. — [Chromatic accessibility](https://www.chromatic.com/docs/accessibility)
- Default rules are WCAG 2.0 A/AA, WCAG 2.1 A/AA and Best Practices, with the `region` rule disabled. `parameters.a11y` has `element`, `config` (passed to `axe.configure`, e.g. `rules[{id, selector, enabled}]`) and `options` (e.g. `runOnly` with tag values such as `EN-301-549`), settable at story, component or project level. `globals.a11y.manual: true` disables automatic checks. — [Chromatic a11y configure](https://www.chromatic.com/docs/accessibility/configure)
- Dashboard (Library, "A11y violations" tab): total violations, components tested and test count, sampled daily. A trend chart shows remediation over time. A component table ranks components by violation count with a severity classification and a "last update" time. CSV export of all violations with component and story details is pitched for VPAT documentation, with impact encoded like "3-critical". Free and standard plans get 7 days of history on the default branch only; Enterprise adds full history and multi-branch tracking. — [Chromatic a11y dashboard](https://www.chromatic.com/docs/accessibility/dashboard)

**Storybook a11y addon test modes**
- `parameters.a11y.test`: `'off'` skips checks (the panel is still available), `'todo'` reports violations as warnings without failing, and `'error'` fails the test. Stories with `'error'` run automatically in CI via the Vitest addon. It can be set globally in `.storybook/preview` or per story. The default is ambiguous across sources: the automigration sets `'todo'`, while the v9 docs list undefined. — [Storybook 9 accessibility testing](https://storybook.js.org/docs/9/writing-tests/accessibility-testing.md); [storybookjs PR #30516](https://github.com/storybookjs/storybook/pull/30516) (search summary)

**Deque axe DevTools: Intelligent Guided Tests (IGT)**
- IGTs: Table, Keyboard, Modal Dialog, Interactive Elements, Images, Structure and Forms. They are driven by "a series of simple questions" and described as "Powered by AI". "Finish" returns to the "Guided Tests" tab. — [Deque IGT docs](https://docs.deque.com/devtools-for-web/4/en/devtools-igt/)
- "Auto Replay": after a completed run, a "Replay" button reuses earlier answers, detects changes, and asks only about what changed (Modal Dialog, Keyboard and Forms only). Progress auto-saves, and "Save progress & quit" leaves an "In Progress" run. Other controls: "Mark as complete or n/a" (blocks new runs, undone with "Re-enable Test"), "Clear this run", "Delete All Runs", and a partial-page scan for large DOMs. — [Deque IGT docs](https://docs.deque.com/devtools-for-web/4/en/devtools-igt/)
- Automated IGTs (AI): the Keyboard IGT auto-tabs and evaluates each tab stop for focus indicator, role and visibility, and detects missing tab stops and keyboard traps. The Table IGT classifies data versus layout tables and finds missing header markup. The Interactive Elements IGT assesses name, role and state. Runs consume AI credits, and the free extension provides only automated testing, one page at a time. — [Deque automated IGTs](https://docs.deque.com/devtools-for-web/4/en/automated-igts/) (search summary)
- A "Remaining Testing" checklist routes the manual checks that IGTs do not cover (e.g. forms collecting personal information) to the user. — [Deque Remaining Testing](https://docs.deque.com/devtools-for-web/4/en/devtools-whatslefttotest/) (search summary)
- The Structure IGT (release 4.17) replaced the former Page Info and Headings IGTs. — [Deque blog: Structure IGT](https://www.deque.com/blog/axe-devtools-updates-ui-improvements-edge-browser-extension-and-a-brand-new-structure-intelligent-guided-test/) (search summary)

**axe Monitor / axe Developer Hub**
- axe Monitor 8.0 (2025-11-06): Scans (formerly "projects") can belong to multiple "Scan Groups". A "Scan Overview" page shows insights and issues by impact. Reports can be grouped by issue or page, viewed by URL or page title, and filtered by any field. Users can compare progress between recent scan runs and track scores and statuses across hundreds of projects. Up to 50K issues export at once as CSV or "axe Universal JSON". Assignee and status can be bulk-updated. Classic View was discontinued. — [Deque: axe Monitor 8.0](https://www.deque.com/axe-monitor-8/)
- axe Developer Hub 2025 release notes: global configuration (Jan), a downloadable-reports REST service and a redesigned project flow (May, with WCAG 2.1 AA as the default standard), new summary and issue-details pages (Jul 17), WCAG category, standard and success-criterion data on mobile results (Sep 30), and axe-core 4.11.0 (Oct 14). — [axe Developer Hub release notes 2025](https://docs.deque.com/developer-hub/2/en/dh-rn-2025)
- The Developer Hub fact sheet says leaders can set accessibility policies that block releases with unresolved issues, and can track improvements over time. — [axe Developer Hub fact sheet](https://accessibility.deque.com/hubfs/Fact%20Sheets/axe-Developer-Hub.pdf) (search summary)
- Deque axe Auditor generates ACR/VPATs for WCAG 2.x (Web) and EN 301 549. — [Deque axe Auditor VPAT generation](https://docs.deque.com/auditor/2.33/en/vpat-generation-overview) (search summary)

**Microsoft Accessibility Insights for Web**
- FastPass is a two-step check meant to take under 5 minutes. Step one, Automated checks (axe-core, about 50 requirements), lists failures by rule, highlights them on the page with a visual-helper toggle, and gives "How to fix" for each. Step two, Tab stops, is an assisted test. — [Accessibility Insights overview](https://accessibilityinsights.io/docs/web/overview/); [FastPass](https://accessibilityinsights.io/docs/web/getstarted/fastpass/)
- "Needs review" lists instances that "need to be reviewed by a human to determine whether they pass or fail", each with "How to check". — [FastPass](https://accessibilityinsights.io/docs/web/getstarted/fastpass/)
- Tab stops: "Show tab stops" draws a circle on the focused element and numbers each element's tab order. Auto-detection raises "Possible failures auto-detected" and adds failure instances (e.g. "Unreachable element"). The checklist covers missing tab stop, keyboard trap, no visible focus, incorrect tab order and unexpected focus movement. Users can "Add a failure instance" or edit and delete instances. — [FastPass](https://accessibilityinsights.io/docs/web/getstarted/fastpass/)
- Issue workflow: "File an issue" goes to GitHub or Azure Boards, "Copy failure details" copies to the clipboard, and "Export result" saves a report. — [FastPass](https://accessibilityinsights.io/docs/web/getstarted/fastpass/)
- Assessment: 24 tests against WCAG 2.2 AA. Requirements are typed Automated, Assisted or Manual. Statuses are Pass, Fail or indeterminate ("Undo" resets). Assisted requirements are marked pass/fail per instance, with "Pass unmarked instances" in bulk. A "Guidance" panel links to the WCAG success criteria. "Save assessment" downloads an `a11ywebassessment` file, "Load assessment" restores one, "Export as HTML" groups by test, and "Export as JSON" groups by success criterion with ISO 8601 dates. — [Accessibility Insights Assessment](https://accessibilityinsights.io/docs/web/getstarted/assessment/)
- Conflict: the overview page says Assessment verifies WCAG 2.1 AA with about 20 manual tests, while the Assessment page says WCAG 2.2 AA with 24 tests. The overview is likely stale. — [overview](https://accessibilityinsights.io/docs/web/overview/) vs [Assessment](https://accessibilityinsights.io/docs/web/getstarted/assessment/)

**Lighthouse CI (assertions, budgets, server)**
- `ci.assert` presets are `lighthouse:all`, `lighthouse:recommended` and `lighthouse:no-pwa`. Levels are `off`, `warn` (exit 0) and `error`. Options are `minScore`, `maxLength` and `maxNumericValue`. `aggregationMethod` is `median`, `optimistic` (default), `pessimistic` or `median-run`. `categories:accessibility` takes `minScore`. `assertMatrix` applies per-URL-pattern assertions (`matchingUrlPattern`). `budgetsFile` points to a budget.json and is exclusive with other assert options. `numberOfRuns` defaults to 3. — [LHCI configuration](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/configuration.md)
- Upload targets: `lhci` server, `temporary-public-storage` or `filesystem`. GitHub status checks are configured via `githubToken`/`githubAppToken`. — [LHCI configuration](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/configuration.md)
- The LHCI server stores history, "displays trends in a dashboard", and has "an in-depth build comparison UI". Storage is SQLite, MySQL or Postgres. A build token can only upload, while an admin token can edit or delete. Optional basic auth. Ships as a Docker image `patrickhulce/lhci-server` on port 9001 and needs Node 22. — [LHCI server](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/server.md)

**Pa11y CI / Pa11y Dashboard**
- Pa11y CI is configured through `.pa11yci` (JSON/JS) with `defaults` plus per-URL overrides (`actions`, `ignore`, `threshold`, `runners`, `viewport`, `includeWarnings`, `includeNotices`, `screenCapture`). Runners are `htmlcs` (default) and `axe`. — [pa11y-ci](https://github.com/pa11y/pa11y-ci)
- `threshold` is the number of issues allowed before a page fails. The CLI also accepts `--threshold`, `--sitemap`, `--sitemap-exclude`, and `concurrency` (default 1). Reporters are `cli` and `json`, plus custom reporters with `beforeAll`/`results`/`afterAll` hooks. Exit codes: 0 = pass, 1 = technical fault, 2 = failures at or above the threshold. Version 5 is current. — [pa11y-ci](https://github.com/pa11y/pa11y-ci)
- Pa11y Dashboard is a web UI over Pa11y Webservice, which uses MongoDB and runs scheduled tests via cron (`WEBSERVICE_CRON`). It has a `readonly` mode, Docker/K8s guidance, v5 requires Node 20+, and v4 support ends May 2026. — [pa11y-dashboard](https://github.com/pa11y/pa11y-dashboard)

**Siteimprove / Level Access (brief)**
- The Siteimprove Accessibility Code Checker became generally available in February 2025 after a November 2024 beta. It works with Selenium, Playwright, Cypress and Puppeteer. The free tier covers local terminal output and CI/CD gating. The paid tier adds code examples, "AI Remediate", content and HTML views, and a dashboard that tracks fixes over time. — [Siteimprove release note Feb 6 2025](https://help.siteimprove.com/support/solutions/articles/80001166886-feb-6th-2025-accessibility-code-checker) (search summary)

### Inferences
- BTP's justified/expiring suppressions are a stricter cousin of Chromatic's "accepted violations baseline". BTP could add a lightweight "known issues baseline" with identity = rule + stable selector or fingerprint + bounding box (Chromatic's three traits). The report would then split results into New, Existing (baselined) and Fixed. Fixes would auto-clear from the baseline, as in Chromatic.
- Per-story severity modes (`off`/`todo`/`error`, as in Storybook) and Lighthouse-style levels (`off`/`warn`/`error`) plus `assertMatrix`-like glob rules per story or component pattern would be familiar to users and simple to implement in BTP config.
- "Needs review" (axe `incomplete`) is surfaced by Accessibility Insights and the Storybook panel but omitted by Chromatic. BTP can differentiate by routing axe `incomplete` results into its existing manual WCAG 2.2 review workflow, with fingerprints so that verdicts go stale when the markup changes. This parallels Deque's "Auto Replay asks only about changes since last run".
- An assisted Tab-stops visualization, as in Accessibility Insights FastPass, is realistic to self-host: Playwright can press Tab, record the focused element boxes, and render numbered circles over the story screenshot. Missing tab stops, traps and no-visible-focus could be flagged by comparing focusable elements with the visited sequence and by diffing focus versus non-focus screenshots.
- The Accessibility Insights Assessment model (Automated, Assisted or Manual requirements; Pass/Fail/indeterminate; per-instance marking; export grouped by success criterion as JSON) is a good schema reference for BTP's manual WCAG 2.2 workflow and for a JSON export.
- Dashboards: Chromatic's design (total violations, components tested, a daily-sampled trend chart, a component table ranked by count and severity, CSV export) is fully reproducible from BTP's local result history. Adding axe Monitor-style "group by issue vs by page/component" and "compare two runs" views is straightforward.
- VPAT/ACR: a "draft ACR" export from BTP is a realistic differentiator for an OSS tool. It would combine automated results and manual WCAG 2.2 verdicts per success criterion. It must be labeled as a draft, since vendors (Level Access, Deque Auditor) produce ACRs via audited workflows.

### Gaps
- axe Developer Hub's exact baseline or "new issues only" mechanics, its GitHub PR checks, and its threshold/policy configuration were not found in the 2025 release notes. Only the fact-sheet claim about policies is available.
- No source found for an accessibility "score" formula in axe Monitor, Chromatic or Pa11y Dashboard. Lighthouse's accessibility category score (0-1, asserted via `minScore`) is the only concrete score.
- The Pa11y Dashboard results-over-time graph and per-issue grouping were not described in the README content retrieved.
- The Lighthouse CI server compare-view specifics (audit diffs, score deltas, branch filters) were not described in the server doc text.
- No 2025-2026 sources were found for a combined Level Access/Siteimprove product or for automated VPAT generation in either product. Coverage is brief, as requested.

## Q4. Table stakes vs differentiators, and what is realistic to self-host in a .NET/Blazor demo site backed by real local results

### Takeaway
Table stakes: baseline vs new with split, overlay and highlight views; per-snapshot accept/reject and a build verdict; a PR status check; masks or ignore regions and thresholds; merge-base or branch-aware baselines; a cross-browser/viewport matrix; and, for a11y, axe results with element highlighting, rule details, fix guidance, and thresholds that fail CI. Differentiators: similar-diff grouping with bulk decisions, persistent decisions, flaky fingerprints and auto-ignore, semantic match levels and RCA, AI triage and summaries, ARIA-tree views, accessibility baselines (only new violations), guided or assisted manual tests with replay, trend dashboards, and ACR export. Almost everything except true Visual-AI and LLM triage and cloud render grids can be self-hosted with BTP's existing local Playwright + bUnit data.

### Inferences

These are prioritized for a self-hosted BTP showcase site backed by real local results.

**Tier 1: table stakes, low effort, all local**
- Diff modes: Split (2-up), Unified overlay with color and opacity controls, Strobe/flicker, Baseline-only/New-only toggles, synced zoom/pan, and an autofocus magnifier for tiny diffs, alongside the existing slider.
- Review states per snapshot (Unreviewed, Accepted, Rejected, Ignored-flaky) and per run (Approved, Changes requested, Rejected). Keyboard shortcuts with a `?` help overlay.
- A filterable matrix grid: rows are stories, columns are browser × viewport × theme, and cells show status with a diff-percent heat. Clicking a cell opens the diff. Percy's "approval covers all browsers/widths" and Chromatic's "baselines are browser-independent" argue for an "accept for all variants of this story" bulk action.
- A11y issue list grouped by rule, impact, WCAG SC or component. Element highlighting on the story screenshot (red boxes, as in Chromatic) using node bounding boxes captured at axe time. A "how to fix" panel taken from axe `helpUrl` and description.
- CI gating: severity modes per story (`off`/`todo`/`error`), Lighthouse-style `warn`/`error` levels, and per-pattern overrides.

**Tier 2: differentiators that are realistic to self-host**
- Diff fingerprints that enable grouping ("N similar" across stories, browsers and themes), bulk accept or reject per group, decisions persisted per (baseline hash, actual hash), and flaky auto-suggest after N occurrences.
- An accessibility baseline with New/Existing/Fixed deltas, complementing expiring suppressions. A trend dashboard (violations over time, components ranked, rule histogram) from the stored history of local runs. CSV/JSON export.
- Axe `incomplete` results turned into "Needs review" items that feed the manual WCAG 2.2 workflow, with existing fingerprint staleness. This is the BTP analog of Deque's Auto Replay.
- A DOM/markup diff panel for changed regions, using bUnit markup and computed styles: a lightweight Applitools RCA.
- An ARIA/accessibility-tree snapshot per story, shown as an alternate view of the visual diff (Argos ARIA view) and diffed as text (Playwright `toMatchAriaSnapshot`).
- Tab-order overlay (FastPass-style numbered circles) captured during the browser run.
- An environment-change banner that compares browser versions recorded with the baseline and with the current run (Happo-style).
- A draft ACR/VPAT-style export per WCAG 2.2 SC, combining automated and manual verdicts. Label it a draft.

**Tier 3: hard or not credible to self-host for a demo**
- AI change classification and natural-language summaries (Percy VRA) need a vision or LLM model. A heuristic DOM-based classifier is the honest substitute.
- A cloud cross-browser render grid (Applitools UFG). BTP's local Chromium/Firefox/WebKit already covers the demo need.
- Org-scale monitoring (axe Monitor Scan Groups, 50K-issue exports, Jira-style bulk assignment) is out of scope for a component-testing demo.
- TurboSnap-like selection (only re-render stories affected by changed files) is feasible but medium effort: it needs a Razor/C# dependency graph from Roslyn or MSBuild. It is a good roadmap item rather than demo-site material.

### Gaps
- No source quantifies which features users value most (e.g. surveys comparing grouping and AI triage). Prioritization above is inference.
- No found source documents a .NET/Blazor-native visual or a11y review UI to benchmark against. BTP appears to have no direct .NET competitor in these sources, but this was not exhaustively verified.
- Pricing tiers for most vendors were not researched, beyond the plan-gating notes above.
